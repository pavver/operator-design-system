# Кастомізація

Як застосунок адаптує компоненти без внесення змін до дизайн-системи.
Модель наслідує усталені вебфреймворки (Quasar, Vuetify): спільні групи пропів, іменовані слоти, метричні змінні для окремих компонентів, замінні рядки та піктограми, а також публічні будівельні блоки.
Кожен наведений нижче механізм є частиною специфікації компонента, тому кожна платформа реалізує ті самі хуки.

Status: **draft** on web.

## Принципи

* Типові значення — це дизайн-система; кастомізація змінює екземпляр, але ніколи не правила.
  Одиниці залишаються DU та TU, кути залишаються прямими, стани підпорядковуються [states.md](states.md).
* Застосунок ніколи не орієнтується на внутрішні імена класів чи структуру елементів.
  Стабільними є лише хуки, перелічені в розділі **Customization** компонента.
* Хук, який має один компонент, мають усі компоненти того самого сімейства з тим самим іменем.

## 1. Кореневі class та style

Кожен компонент приймає `class` та `style` на своєму кореневому елементі.
`class` додається до власних класів компонента; `style` додається після власного інлайн-стилю компонента, тому він має вищий пріоритет.

| Платформа | Еквівалент |
| :--- | :--- |
| Web | пропи `class`, `style` на кореневому елементі. |
| Compose | параметр `modifier`. |
| egui | немає; використовуйте метричні пропи. |

## 2. Метричні пропи

Кожен відступ і розмір, який малює компонент, є пропом.
Метричний проп — це число в DU (просторові значення) або TU (розміри шрифту, висота рядка).
Невстановлений проп зберігає значення дизайн-системи.

У вебі кожен метричний проп підтримується користувацькою властивістю CSS з назвою `--op-<family>-<metric>`, що зчитується з токеном як запасним варіантом, наприклад `height: var(--op-field-height, var(--op-dim-row-standard))`.
Проп записує змінну на корені компонента, тому:

* один екземпляр змінюється через проп (`height=8.0`);
* ціле піддерево змінюється через змінну в CSS застосунку (`.my-table { --op-field-height: calc(var(--op-du) * 8); }`);
* змінні сімейства є спільними: кожне поле читає `--op-field-*`, кожна кнопка — `--op-button-*`.

Кольори не є пропами.
Компонент зчитує свої кольори через змінні `--op-<family>-<role>` із запасними варіантами токенів, тому застосунок може перефарбувати піддерево за допомогою токенів, якими володіє, тоді як кожна тема зберігає однаковий набір токенів.

Кожна специфікація компонента перелічує свої метричні пропи та змінні кольорів у таблиці **Customization**.

## 3. Слоти

Слот — це іменоване місце, куди викликач вставляє власний вміст.
Імена слотів є спільними для сімейств:

| Сімейство | Слоти |
| :--- | :--- |
| Fields | `prepend`, `append` (всередині поля), `before`, `after` (зовні поля), `label_slot`, `hint_slot`. |
| Buttons | `leading`, `trailing`, `content` (замінює текст). |
| Lists and menus | `option` (з областю видимості: отримує елемент), `empty`, `before_options`, `after_options`, `header`, `footer`. |
| Containers (dialogs, sheets, cards, panels) | `header`, `actions`, `footer`, типові дочірні елементи. |

Слот з областю видимості отримує дані від компонента, наприклад варіант, який він рендерить.

| Платформа | Слот | Слот з областю видимості |
| :--- | :--- | :--- |
| Web | `Slot` (замикання або `ViewFn`) | `ScopedSlot<T>` (`Callback<T, AnyView>`) |
| Compose | `@Composable () -> Unit` | `@Composable (T) -> Unit` |
| egui | `FnOnce(&mut Ui)` | `FnMut(&mut Ui, &T)` |

## 4. Рядки

Компоненти ніколи не показують захардкоджений текст.
Кожен вбудований текст (мітки кнопок, доступні назви, плейсхолдери, назви місяців) має ключ, як-от `search-field.clear`, та англійське типове значення.
Порядок розв'язання: проп компонента, потім пошук ключа застосунком, потім англійське типове значення.

Застосунок надає один пошук для всього дерева через корінь теми (`ThemeRoot strings=...` у вебі); він зчитує свою поточну мову всередині пошуку, тому кожен рядок слідує за зміною мови.
Кожна специфікація перелічує свої ключі в таблиці **Strings**.

## 5. Піктограми

Вбудовані піктограми — це семантичні ключі (`field.clear`, `search-field.search`, `menu.submenu`) із типовим символом.
Порядок розв'язання: проп компонента, потім пошук піктограми для ключа застосунком (`ThemeRoot icons=...`), потім типове значення.
Кожна специфікація перелічує свої ключі в таблиці **Icons**.

## 6. Будівельні блоки

Примітиви, з яких будуються компоненти, є публічними, тому застосунок може побудувати власний компонент, який виглядає та поводиться як нативний:

* `Field`: оболонка поля (мітка, поле з межею стану та слотами, підказка й помилка).
* `Popover`: розміщення прикріпленого оверлею.
* `VirtualList`: віконний рендеринг списку.
* Візуальні елементи стану (`use_state_visual`), `AsyncAction`, `JobToken`, ripple, spinner.

## 7. Каскад стилів (веб)

Весь CSS компонентів знаходиться всередині одного шару каскаду, `@layer operator`.
Тому CSS застосунку без шарів завжди перемагає стилі компонентів незалежно від специфічності селектора, і `!important` не потрібен.
Застосунок, який має власні глобальні правила для елементів (`button { ... }`), повинен розміщувати їх у шарі, оголошеному перед `operator` (`@layer reset, operator;`), щоб вони не перевизначали компоненти.
