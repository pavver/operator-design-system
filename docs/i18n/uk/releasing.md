# Випуск версій

Кожен випуск публікує дві речі:

* GitHub Release з примітками, згенерованими з Conventional Commits, та зібраним сайтом документації у вигляді zip-файла.
* Сайт документації на GitHub Pages: <https://pavver.github.io/operator-design-system/>.

Сайт розгортається лише релізами, тому публічна сторінка завжди відповідає випущеній версії.

## Версіонування

Репозиторій дотримується семантичного версіонування з однією версією для всього робочого простору.
Поки версія `0.x`, мінорна зміна версії може змінювати поведінку компонентів або API.

| Зміна | Підвищення |
| :--- | :--- |
| Новий компонент, новий токен, нова платформа | minor |
| Виправлення помилки, документація | patch |
| Видалений або перейменований токен чи API (після `1.0`) | major |

## Кроки

1. Переконайтеся, що `main` містить усе для випуску та CI зелений.
2. Запустіть скрипт випуску з чистого `main`:

   ```bash
   scripts/release.sh 0.2.0 --push
   ```

   Він встановлює версію робочого простору та прив'язки `tag = "vX.Y.Z"` у README.md, запускає ті самі перевірки, що й CI, створює коміт `chore(release): v0.2.0`, створює тег і надсилає їх обох.
3. [Робочий процес випуску](../.github/workflows/release.yml) перевіряє відповідність тегу версії робочого простору, збирає сайт документації, публікує випуск і розгортає GitHub Pages.

## Примітки до випуску

Примітки генеруються [git-cliff](https://git-cliff.org) за допомогою [cliff.toml](../cliff.toml).
Включаються лише Conventional Commits, згруповані за типом.
Пишіть теми комітів так, щоб вони добре читалися в примітках.

## Історія змін компонентів

Кожен коміт, що змінює компонент, додає один файл за шляхом `docs/changes/<component>/<YYYY-MM-DD>-<HHMM>-<short-kebab-slug>.toml`.
Назва каталогу компонента відповідає назві його специфікації в kebab-форматі у `docs/components/`.
Використовуйте у назві файла місцеві дату й час із поля `date`.
Кожен файл починається як `draft`; під час перевірки супроводжувач затверджує його, замінює остаточним описом або видаляє, якщо зміну відкинуто.
Сторінка [Зміни для перевірки](changes-to-review.md) показує всі чернетки компонентів від найновіших до найстаріших із посиланнями на специфікації та приклади.
Сторінка кожного компонента зберігає повну історію, включно із затвердженими змінами, щоб полегшити перехід між випусками.

```toml
date = "2026-11-22T14:30:00+02:00"
status = "draft"
kind = "breaking"

[en]
summary = "Rename the `label` prop to `aria_label`."
check = "Open the accessible-name example and inspect its label."
migration = "Replace `label` with `aria_label` at call sites."

[uk]
summary = "Перейменовано проп `label` на `aria_label`."
check = "Відкрийте приклад доступної назви та перевірте його підпис."
migration = "Замініть `label` на `aria_label` у місцях виклику."
```

Поле `date` вимагає часову позначку RFC 3339 зі зміщенням UTC, а `status` приймає лише `draft` або `approved`.
Обов’язкове поле `kind` приймає `new`, `feature`, `fix`, `breaking`, `docs` або `refactor`.
Обидві мовні таблиці вимагають `summary` у Markdown.
Додайте локалізоване поле `check`, щоб указати тестувальникам приклад, стан або проп для перевірки, та локалізоване поле `migration`, щоб пояснити потрібні дії користувачів.
Для змін виду `breaking` поле `migration` обов’язкове обома мовами.
Відносні посилання Markdown у всіх текстах змін обчислюються від `docs/components/`, тому `[Field](field.md)` веде до специфікації Field.
Невідомі поля спричиняють помилку.
Необов’язкове поле `commit` приймає 7–40 шістнадцяткових символів.
Коли його пропущено, збирання може додати посилання на коміт, що створив файл, за історією Git; якщо Git недоступний або клон поверхневий, посилання мовчки пропускається.

## Повторне розгортання сайту

Запустіть робочий процес випуску вручну на вкладці Actions і виберіть тег.
Ручний запуск розгортає сайт без створення випуску.
